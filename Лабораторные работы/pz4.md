# Лабораторная работа № 4

**Модуль 4. Безопасность и обслуживание Kubernetes**

## Цель лабораторной работы

Освоить основные механизмы защиты и обслуживания Kubernetes-кластера на базе K3s. Научиться ограничивать права доступа с помощью Role-Based Access Control (RBAC), применять политики безопасности Pod, безопасно использовать и обновлять Secrets, управлять конфигурациями приложений через ConfigMap, проверять шифрование секретных данных и диагностировать неисправности Kubernetes.

**Ожидаемый результат:** в Kubernetes развёрнуто защищённое веб-приложение с ограниченными привилегиями контейнеров, настроены RBAC и Pod Security Admission, выполнены обновление конфигурации и ротация учебного Secret, проверено состояние шифрования секретных данных и устранена искусственно созданная неисправность приложения.

## Подсказки по ключевым частям

### Проверка кластера и подготовка рабочего пространства

```bash
sudo systemctl status k3s
sudo k3s kubectl get nodes
sudo k3s kubectl get pods -A
sudo k3s kubectl config current-context
sudo k3s kubectl auth can-i '*' '*' --all-namespaces

mkdir -p ~/k8s-lab4
cd ~/k8s-lab4

sudo k3s kubectl create namespace lab4
```

Последняя команда проверки разрешений требует достаточно привилегированного контекста. Не используйте полученный административный kubeconfig для обычных приложений.

### Настройка RBAC

Создайте `rbac.yaml`:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: lab4-reader
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: lab4-pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: lab4-reader-binding
subjects:
  - kind: ServiceAccount
    name: lab4-reader
    namespace: lab4
roleRef:
  kind: Role
  name: lab4-pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Примените манифест:

```bash
sudo k3s kubectl -n lab4 apply -f rbac.yaml
```

Проверьте разрешения:

```bash
sudo k3s kubectl auth can-i list pods \
  --as=system:serviceaccount:lab4:lab4-reader -n lab4

sudo k3s kubectl auth can-i delete pods \
  --as=system:serviceaccount:lab4:lab4-reader -n lab4

sudo k3s kubectl auth can-i list secrets \
  --as=system:serviceaccount:lab4:lab4-reader -n lab4
```

Ожидаемые результаты: `yes`, `no`, `no`.

Для проверки прав другого пространства имён выполните аналогичный запрос с `-n default`. Ожидаемый ответ — `no`, если ServiceAccount не имеет дополнительных разрешений.

Проверка с `--as` использует механизм impersonation и должна выполняться от имени администратора, имеющего соответствующие полномочия.

### Настройка Pod Security Admission

Примените политику `Restricted` к пространству имён:

```bash
sudo k3s kubectl label namespace lab4 \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted \
  --overwrite
```

Создайте файл `insecure-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: insecure-test
spec:
  containers:
    - name: test
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
```

Попробуйте применить:

```bash
sudo k3s kubectl -n lab4 apply -f insecure-pod.yaml
```

При работающей политике `enforce=restricted` создание Pod должно быть отклонено. Изучите сообщение и исправьте манифест.

Для исправления используйте следующий набор параметров:

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  runAsGroup: 10001
  seccompProfile:
    type: RuntimeDefault
```

Этот блок добавляется в `spec` Pod. Отдельно в описание контейнера необходимо добавить:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL
```

Дополнительно можно использовать `readOnlyRootFilesystem: true`, если приложению не требуется запись в корневую файловую систему.

### Развёртывание защищённого приложения

Создайте `deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lab4-web
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: lab4-web
  template:
    metadata:
      labels:
        app: lab4-web
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: web
          image: busybox:1.36
          command: ["/bin/sh", "-c"]
          args:
            - 'echo "Web server started"; exec httpd -f -p 8080 -h /www'
          ports:
            - containerPort: 8080
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL
          env:
            - name: APP_MESSAGE
              valueFrom:
                configMapKeyRef:
                  name: lab4-config
                  key: APP_MESSAGE
            - name: APP_TOKEN
              valueFrom:
                secretKeyRef:
                  name: lab4-secret
                  key: app-token
          resources:
            requests:
              cpu: 20m
              memory: 16Mi
            limits:
              cpu: 100m
              memory: 64Mi
          readinessProbe:
            httpGet:
              path: /
              port: 8080
            periodSeconds: 5
          volumeMounts:
            - name: web-content
              mountPath: /www
              readOnly: true
      volumes:
        - name: web-content
          configMap:
            name: lab4-config
```

Приложение использует порт `8080`, не требующий привилегий для привязки к низким портам. Контейнер не запускается от root и не получает полный набор Linux capabilities.

Создайте `service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: lab4-web
spec:
  type: ClusterIP
  selector:
    app: lab4-web
  ports:
    - port: 80
      targetPort: 8080
```

Примените файлы:

```bash
sudo k3s kubectl -n lab4 apply -f deployment.yaml
sudo k3s kubectl -n lab4 apply -f service.yaml

sudo k3s kubectl -n lab4 rollout status deployment/lab4-web
sudo k3s kubectl -n lab4 get pods
sudo k3s kubectl -n lab4 get svc
```

Для проверки в браузере запустите:

```bash
sudo k3s kubectl -n lab4 port-forward \
  service/lab4-web 8080:80
```

Откройте `http://localhost:8080`.

Обновление файлов ConfigMap, подключённых как обычный том, происходит с некоторой задержкой. Выполните повторную проверку, если сразу после изменения видна старая версия.

Проверьте переменную окружения:

```bash
sudo k3s kubectl -n lab4 exec deployment/lab4-web -- \
  printenv APP_MESSAGE
```

До пересоздания Pod значение переменной окружения должно остаться прежним.

Выполните:

```bash
sudo k3s kubectl -n lab4 rollout restart deployment/lab4-web

sudo k3s kubectl -n lab4 rollout status deployment/lab4-web
```

После завершения обновления повторно проверьте `APP_MESSAGE`.

### Обновление Secret

Обновите учебный токен:

```bash
printf '%s' 'lab4-demo-v2' | \
sudo k3s kubectl -n lab4 create secret generic lab4-secret \
  --from-file=app-token=/dev/stdin \
  --dry-run=client -o yaml | \
sudo k3s kubectl -n lab4 apply -f -
```

Проверьте, что переменная существует:

```bash
sudo k3s kubectl -n lab4 exec deployment/lab4-web -- \
  sh -c 'test -n "$APP_TOKEN" && echo TOKEN_PRESENT'
```

До перезапуска Pod по-прежнему будет использовать старое значение переменной окружения.

Выполните перезапуск:

```bash
sudo k3s kubectl -n lab4 rollout restart deployment/lab4-web

sudo k3s kubectl -n lab4 rollout status deployment/lab4-web
```

Для проверки учебного значения без его вывода:

```bash
sudo k3s kubectl -n lab4 exec deployment/lab4-web -- \
  sh -c 'test "$APP_TOKEN" = "lab4-demo-v2" && echo TOKEN_UPDATED'
```

### Проверка шифрования Secret в K3s

На управляющем узле выполните:

```bash
sudo k3s secrets-encrypt status
```

Результат позволит определить, включено ли шифрование Secret при хранении.

В K3s для этой функции используется параметр конфигурации:

```yaml
secrets-encryption: true
```

В стандартной установке K3s без соответствующей настройки шифрование Secret при хранении не следует считать включённым.

**Дополнительно, только на отдельном учебном кластере:** если шифрование уже включено и имеется проверенная резервная копия, изучите выполнение ротации ключей:

```bash
sudo k3s secrets-encrypt rotate-keys
sudo k3s secrets-encrypt status
```

Не выполняйте эти команды на используемом другими студентами кластере. Процедура зависит от версии K3s и количества управляющих узлов; в некоторых конфигурациях требуются последовательные перезапуски серверов.

### Диагностика ошибки ImagePullBackOff

Создайте неисправность:

```bash
sudo k3s kubectl -n lab4 set image \
  deployment/lab4-web web=busybox:lab4-no-such-tag
```

Посмотрите состояние Pod:

```bash
sudo k3s kubectl -n lab4 get pods
sudo k3s kubectl -n lab4 get replicasets
```

Найдите проблемный Pod и выполните:

```bash
sudo k3s kubectl -n lab4 describe pod ИМЯ_POD
```

В разделе `Events` найдите сообщение об ошибке загрузки образа.

Для проверки Deployment:

```bash
sudo k3s kubectl -n lab4 rollout status \
  deployment/lab4-web --timeout=45s
```

При неудачном обновлении команда может завершиться с ошибкой по тайм-ауту. Это ожидаемый результат.

Восстановите приложение:

```bash
sudo k3s kubectl -n lab4 rollout undo deployment/lab4-web

sudo k3s kubectl -n lab4 rollout status deployment/lab4-web
```

Проверьте:

```bash
sudo k3s kubectl -n lab4 get pods
sudo k3s kubectl -n lab4 get deployments
```

## Что изменить, чтобы выполнить лабораторную работу на Kubernetes (K8s) вместо K3s

K3s является дистрибутивом Kubernetes, поэтому механизмы RBAC, Pod Security Admission, ConfigMap, Secret, Deployment и Service работают через тот же Kubernetes API. Отличия относятся главным образом к конфигурации управляющей плоскости и обслуживанию кластера.

### 1. Заменить команды управления

Вместо:

```bash
sudo k3s kubectl get nodes
```

используйте:

```bash
kubectl get nodes
```

Во всех остальных командах замените `sudo k3s kubectl` на `kubectl`, предварительно настроив доступ к кластеру.

### 2. Проверить Pod Security Admission

В K3s и стандартном Kubernetes доступны одинаковые уровни Pod Security Standards.

Для проверки используйте:

```bash
kubectl get namespace lab4 --show-labels
```

Метки политик безопасности остаются прежними. Однако в управляемых или индивидуально настроенных кластерах могут действовать дополнительные политики безопасности, которые влияют на создание Pod.

### 3. Оставить RBAC без изменений

Манифест `rbac.yaml` менять не требуется.

В Kubernetes используются те же объекты ServiceAccount, Role и RoleBinding, а также команды `kubectl auth can-i`.

### 4. Заменить механизм настройки шифрования Secret

В K3s предусмотрен встроенный механизм:

```bash
sudo k3s secrets-encrypt status
```

В обычном Kubernetes, развёрнутом через `kubeadm`, такой команды нет.

Шифрование Secret при хранении настраивается на уровне API Server с помощью конфигурации провайдера шифрования и параметра `--encryption-provider-config`.

Для управления ключами необходимо учитывать конфигурацию всех экземпляров API Server и хранилища данных. Изменение параметров шифрования относится к административному обслуживанию кластера, а не к обычным операциям с Secret через `kubectl`.

В управляемых Kubernetes-сервисах механизмы шифрования могут предоставляться платформой. Проверяйте их через документацию и административные инструменты соответствующего сервиса.

### 5. Заменить диагностику системной службы

В K3s применяется:

```bash
sudo journalctl -u k3s -n 50 --no-pager
```

В Kubernetes, созданном через `kubeadm`, для проверки Kubelet используйте:

```bash
sudo systemctl status kubelet
sudo journalctl -u kubelet -n 50 --no-pager
```

Для диагностики управляющей плоскости также проверяйте системные Pod и журналы соответствующих компонентов.

### 6. Оставить конфигурацию приложения без изменений

Файлы `rbac.yaml`, `configmap.yaml`, `deployment.yaml` и `service.yaml` в общем случае не требуют изменений.

Операции обновления ConfigMap, ротации учебного Secret, проверки RBAC, создания защищённых Pod и устранения ошибок выполняются аналогично.

**Итог:** при переходе с K3s на стандартный Kubernetes меняются способ обращения к кластеру, инструменты диагностики управляющей плоскости и администрирования шифрования. Практические задания по RBAC, Pod Security, Secret, ConfigMap и диагностике приложений сохраняются.

## Советы по улучшению работы

**Применяйте принцип минимальных привилегий.** Предоставляйте ServiceAccount только необходимые разрешения. Избегайте широких правил с символом `*`, особенно для операций с Secret и объектами уровня всего кластера.

**Ограничивайте права контейнеров.** Используйте запуск без root, запрет повышения привилегий, ограничение Linux capabilities и Seccomp. Не предоставляйте контейнерам привилегированный режим без технической необходимости.

**Не храните секретные значения в исходном коде.** Применяйте Kubernetes Secret или специализированные системы управления секретами. Учитывайте, что Base64 — это кодирование, а не шифрование.

**Планируйте обновление конфигурации.** Изучайте поведение ConfigMap и Secret при изменении значений. Если приложение получает параметры через переменные окружения, предусмотрите управляемое пересоздание Pod.

**Проверяйте настройки шифрования.** Для рабочих систем используйте шифрование секретных данных при хранении, защищайте ключи и проверяйте резервные копии перед операциями ротации.

**Используйте последовательную диагностику.** При неисправности сначала проверяйте состояние Deployment и Pod, затем события, журналы контейнеров и только после этого системные журналы узлов.

**Сохраняйте рабочие конфигурации.** Поддерживайте YAML-манифесты в актуальном состоянии. Это позволяет быстро восстановить приложение и избежать расхождений между файлами проекта и фактическим состоянием Kubernetes.
